Реліз 2026.2.4 [плагіна для SaltStack](https://plugins.jetbrains.com/plugin/30291-saltstack) великий: нові можливості є для Pillar, для Jinja всередині SLS і для state-файлів. Мета в усіх змін одна. Помилки, які зараз видно тільки після `state.apply`, `state.show_sls` чи `pillar.items` на міньйоні, IDE має показувати ще під час редагування.

Нижче розібрано всі нові можливості з прикладами.

## Pillar

До цього релізу плагін бачив у Pillar-файлах звичайний YAML. Тепер для них є окремий набір перевірок, який працює для всіх Pillar SLS, крім `top.sls`.

### Структура файлу

Salt очікує, що Pillar-файл після рендеру стане словником, а `include:` буде списком. Якщо це не так, помилка з'явиться тільки під час рендеру на мастері. Плагін тепер перевіряє це одразу:

```yaml
# ❌ корінь не є мапою
- nginx
- postgres
```

```yaml
# ❌ include записано рядком, а не списком
include: common.base

# ❌ кілька ключів в одному елементі списку
include:
  - common.base
    apps.web: {}
```

Що враховано:

- **Хибні корені дозволені.** Файл, який рендериться в `null`, `false` або `0`, Salt вважає порожнім Pillar, тому помилки тут немає.
- **Кілька YAML-документів** (`---`) в одному Pillar-файлі позначаються як помилка: Salt такий файл не прочитає.
- **Jinja не дає хибних спрацювань.** Корінь, обгорнутий у `{% if %}`, `{% macro %}` чи блочний `{% set %}...{% endset %}`, не вважається помилкою. Вміст макросів і блочних `set` перевірками структури не аналізується, бо це ще не дані Pillar.
- **Шаблонні елементи `include:`** на зразок `- {{ grains.os_family | lower }}` пропускаються, а статичні елементи поруч з ними перевіряються як завжди.

Для двох найчастіших помилок є quick fix (Alt+Enter):

- **Wrap into list** перетворює `include: common.base` на список з одним елементом;
- **Split include item** розбиває елемент з кількома ключами на окремі елементи списку.

Обидва зберігають відступи та коментарі.

### Ключі за правилами YAML 1.1

Тут найменш очевидна частина. Salt парсить YAML за специфікацією 1.1, а потім працює з результатом як зі словником Python. Тому ключі, які в редакторі виглядають різними, для Salt можуть бути одним ключем, і останнє значення мовчки перезапише попереднє.

Плагін нормалізує кожен ключ так само, як це зробить Salt, і показує такі дублікати:

```yaml
ports:
  80: http
  0x50: http-alt      # дублікат: 0x50 == 80
  0120: http-octal    # дублікат: вісімкове 0120 == 80
  1:20: legacy        # дублікат: шістдесяткове 1:20 == 80

flags:
  true: enabled
  1: one              # дублікат: у Python True == 1
  false: disabled
  0: zero             # дублікат: False == 0

names:
  a: plain
  "\x61": escaped     # дублікат: "\x61" декодується в "a"
```

Нормалізація підтримує:

- цілі числа в десятковому, вісімковому, шістнадцятковому, двійковому та шістдесятковому записі;
- дробові числа, зокрема `.5`, `.inf`, `.nan`;
- булеві значення YAML 1.1 і їхню рівність `1` та `0`, як у Python;
- escape-послідовності в рядках у подвійних лапках.

Крім дублікатів, перевіряються порожні ключі, зарезервовані імена та невідповідність типів ключів.

Дублікати в гілках `{% if %}` / `{% else %}` помилкою не вважаються: на рендері залишиться тільки одна гілка. Ключі, що генеруються Jinja, теж пропускаються.

Стандартна перевірка дублікатів YAML у JetBrains про ці правила нічого не знає. Тому в Pillar-файлах для статичних ключів її вимкнено, щоб не було двох попереджень про одне й те саме.

### Автодоповнення та навігація для `include:`

`include:` у Pillar тепер працює так само зручно, як і в state-файлах:

```yaml
include:
  - common.base   # Ctrl+Click → common/base.sls
  - apps          # Ctrl+Click → apps/init.sls
  -               # Ctrl+Space: список доступних Pillar SLS
```

- Шляхи пропонуються з налаштованих `pillarRoots` у вигляді через крапку: `common.base`, `apps.web`.
- `apps/init.sls` показується як `apps`, як це робить сам Salt.
- Автодоповнення працює і в порожньому елементі після вже записаних, тож список можна дописувати не виходячи з потоку.
- Якщо `pillarRoots` не налаштовано, плагін шукає каталог `pillar` у проєкті.
- State-файли й надалі використовують `fileRoots`, тому Pillar і states не змішуються в підказках.

## Jinja у SLS: дані з `import_yaml` і `import_json`

Типовий патерн у формулах: тримати значення за замовчуванням в окремому YAML чи JSON і імпортувати їх у шаблон. Раніше змінна після `{% import_yaml %}` для IDE була непрозорою. Тепер плагін читає імпортований файл і розуміє його структуру.

```jinja
{% import_yaml "nginx/defaults.yaml" as defaults %}
{% import_json "nginx/upstreams.json" as upstreams %}

worker_processes {{ defaults.nginx.workers }};   {# Ctrl+Click → ключ workers #}
server {{ upstreams.servers[0].host }};          {# елементи списків теж #}
log_level {{ defaults["log-level"] }};           {# ключ з дефісом #}
```

Що вміє плагін:

- **Автодоповнення ключів** на будь-якій глибині: після `defaults.` ви бачите ключі верхнього рівня, після `defaults.nginx.` вкладені.
- **Індекси та елементи списків.** Для YAML-послідовностей і JSON-масивів пропонуються індекси, а після `[0].` поля конкретного елемента.
- **Дужкова нотація там, де вона потрібна.** Якщо ключ не можна записати через крапку (дефіс, пробіл, крапка всередині, починається з цифри), автодоповнення одразу вставить `defaults["log-level"]` замість синтаксично некоректного `defaults.log-level`.
- **Навігація до даних.** Ctrl+Click на `workers` веде на рядок `workers:` у `defaults.yaml`, а не просто на файл.
- **Шляхи імпорту** шукаються і в контексті states (`fileRoots`), і в контексті Pillar (`pillarRoots`). Навігація працює й тоді, коли `{% import_yaml %}` записано всередині `{% if %}`.
- **Аліаси.** Якщо змінну перепризначено через `{% set cfg = defaults.nginx %}`, автодоповнення та навігація працюють і через `cfg`.

Плагін аналізує тільки статичні звернення. Якщо ключ обчислюється динамічно (`defaults[grains.os]`), підказок не буде, і хибних помилок теж.

## Змінні SLS-контексту

Під час рендеру SLS Salt передає в шаблон змінні, які описують сам файл. Плагін тепер знає всі дев'ять:

| Змінна         | Що означає                                   | Приклад для `salt/web/nginx/init.sls` |
|----------------|----------------------------------------------|---------------------------------------|
| `sls`          | ім'я SLS через крапку                        | `web.nginx`                           |
| `slspath`      | каталог SLS відносно кореня                  | `web/nginx`                           |
| `sls_path`     | `slspath` з `_` замість `/`                  | `web_nginx`                           |
| `slsdotpath`   | `slspath` з `.` замість `/`                  | `web.nginx`                           |
| `slscolonpath` | `slspath` з `:` замість `/`                  | `web:nginx`                           |
| `tplfile`      | шлях до файлу шаблону відносно кореня        | `web/nginx/init.sls`                  |
| `tpldir`       | каталог шаблону відносно кореня (Salt 3005+) | `web/nginx`                           |
| `tpldot`       | `tpldir` з `.` замість `/`                   | `web.nginx`                           |
| `tplpath`      | абсолютний шлях до шаблону в кеші міньйона   | відомий тільки під час рендеру        |

**Quick Documentation (Ctrl+Q)** на змінній показує не тільки опис, а й значення, яке вона матиме саме в цьому файлі. Плагін обчислює його з розташування файлу відносно налаштованих коренів Salt. Різницю між схожими змінними видно одразу. Наприклад, у `web/nginx/config.sls` `sls` буде `web.nginx.config`, а `slspath` і `tpldir` будуть `web/nginx`.

Окремо враховано файли, що лежать прямо в корені. Для `tplpath` значення не вигадується: документація пояснює, що абсолютний шлях відомий тільки під час виконання.

**Контекст має значення.** Ці змінні існують тільки під час рендеру SLS. У звичайних Jinja-шаблонах, які розгортаються через `file.managed` з `template: jinja`, їх немає. Тому плагін тепер розрізняє ці два контексти:

- у `.sls` під коренями Salt змінні пропонуються в автодоповненні й не підсвічуються як невизначені;
- у шаблонах файлів вони не пропонуються, а їхнє використання позначається як невизначена змінна. Це саме та помилка, яку інакше ви побачите тільки на міньйоні.

## State-файли

### Нові requisites

Плагін тепер підтримує всі форми requisites, які є в Salt, з автодоповненням модулів і state ID, валідацією та Quick Documentation.

**`listen_in`** працює як дзеркальна версія `listen`. Документація пояснює, як він викликає `mod_watch` наприкінці запуску.

**`*_any`**: `require_any`, `watch_any`, `onchanges_any`, `onfail_any`. Умова виконується, якщо спрацював хоча б один з перелічених станів:

```yaml
start_app:
  cmd.run:
    - name: /opt/app/start.sh
    - require_any:
      - pkg: app_from_repo
      - file: app_from_tarball
```

**`onfail_all`** спрацьовує, тільки якщо впали **всі** перелічені стани. Документація окремо пояснює різницю з `onfail` (логіка «І» проти «АБО»).

**Голі state ID.** Requisite можна записати без модуля, тільки ID. Тепер такі ID теж автодоповнюються з поточного файлу і перевіряються:

```yaml
nginx_service:
  service.running:
    - name: nginx
    - require:
      - nginx_pkg        # Ctrl+Space пропонує ID з файлу
      - missing_state    # ⚠ unresolved state ID
```

**Wildcards.** Шаблони `*`, `?` і `[ ]` у requisites (`- file: /etc/nginx/conf.d/*`) більше не дають хибного «unresolved ID».

**Скаляри там, де потрібен список.** `require_in`, `require_any` та інші reverse- і alternative-requisites приймають тільки список. Запис `- require_in: nginx` тепер позначається як помилка.

### Глобальні аргументи станів

Набір глобальних аргументів розширено до 17. Для всіх є автодоповнення, Quick Documentation і перевірка. Нові: `umask`, `parallel`, `reload_modules`, `reload_pillar`, `reload_grains`, `fire_event`, `cmd_opts_exclude`, `saltenv`.

Перевірки стали точнішими:

- `onlyif` / `unless` приймають і рядкові команди, і форму-мапу з викликом модуля;
- у `retry` перевіряються ключі (`attempts`, `until`, `interval`, `splay`);
- `order: first` розпізнається як коректне значення поряд з числами.

### Перевірка типів аргументів

Типи аргументів state-функцій тепер перевіряються за метаданими Salt: рядок, список, мапа, булеве значення, ціле число, число.

```yaml
web_packages:
  pkg.installed:
    - pkgs: nginx        # ⚠ очікується список
    - refresh: yes       # ✔ boolean у YAML 1.1
```

Аргументи, значення яких генерує Jinja, не перевіряються: їхній тип до рендеру невідомий.

### Структура декларації

Плагін перевіряє базові правила, за якими Salt будує high data: у декларації кожен модуль трапляється один раз і має рівно одну функцію.

```yaml
nginx:
  pkg.installed: []
  pkg.latest: []         # ❌ модуль pkg уже оголошено
  service:
    - running
    - dead               # ❌ дві функції для одного модуля
```

### Дублікати state ID

- Однаковий ID двічі в одному файлі позначається помилкою.
- Однаковий ID у різних файлах (які Salt потім злиє в одне дерево) позначається попередженням.
- Не враховуються ID у взаємовиключних гілках `{% if %}`, ID, згенеровані Jinja, і ID в `extend`, бо там повтор якраз очікуваний.

### Цикли в requisites

Плагін будує граф залежностей між станами і знаходить цикли до запуску:

```yaml
app_config:
  file.managed:
    - name: /etc/app.conf
    - require:
      - service: app_service   # ❌ цикл: app_config → app_service → app_config

app_service:
  service.running:
    - name: app
    - watch:
      - file: app_config
```

Вузлом графа є пара «модуль + ID». Тому типовий для Salt патерн `pkg: nginx` + `service: nginx` + `file: nginx` з однаковим ID не дає хибного циклу.

### Jinja-плейсхолдери

Якщо шлях в `include:`, ID в requisite або `salt://`-URL генерується Jinja, на місці виразу плагін бачить службовий плейсхолдер. Раніше це давало хибні «unresolved»:

```yaml
include:
  - {{ slsdotpath }}.config

nginx_conf:
  file.managed:
    - source: salt://{{ tpldir }}/files/nginx.conf
    - require:
      - pkg: {{ pkg_name }}
```

Тепер такі значення пропускаються, а статичні поруч перевіряються як раніше.

## Продуктивність і стабільність

- **Немає зависань через метадані.** Якщо сервер метаданих Salt відповідав повільно, відкриття налаштувань метаданих блокувало UI до 17 секунд. Тепер статус оновлюється у фоні.
- **Фонове завантаження метаданих.** Перше автодоповнення у state-файлі більше не чекає, поки завантажаться метадані: вони підтягуються у фоні, а підказки з'являються, щойно дані готові.
- **Звіти про помилки.** Додано інтеграцію із Sentry та стандартний обробник помилок JetBrains Marketplace. Якщо в плагіні станеться виняток, звіт можна надіслати прямо з вікна помилки IDE. Збираються тільки помилки самого плагіна.
