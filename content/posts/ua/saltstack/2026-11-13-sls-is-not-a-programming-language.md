У міру розвитку SaltStack-проєкту SLS-файли часто починають виконувати дедалі більше завдань. Спочатку в них є лише встановлення пакета й керування конфігураційним файлом. Потім з'являються умови для різних операційних систем, цикли для створення однотипних ресурсів, перетворення вхідних даних, перевірка поточного стану через shell-команди та багатокрокові процедури оновлення.

Кожна окрема зміна може здаватися виправданою. Однак поступово SLS перестає бути декларативним описом стану й перетворюється на основну мову реалізації deployment logic.

Головна теза цієї статті:

> SLS призначений для опису бажаного стану та композиції states. Він не повинен ставати місцем реалізації алгоритмів розгортання, нормалізації даних, виявлення стану й керування багатокроковими процесами.

Це не означає, що в SLS заборонені Jinja, умови чи цикли. Межа проходить не між «простим» і «складним» синтаксисом, а між різними видами відповідальності.

## Що відбувається під час виконання SLS

SLS-файл не виконується як звичайна програма. Спочатку шаблонізатор, найчастіше Jinja, формує структуру даних. Потім Salt компілює її в набір low chunks і будує граф states. Після цього state modules порівнюють бажаний стан із поточним і виконують потрібні зміни.

```text
Pillar і grains
       ↓
рендеринг Jinja
       ↓
скомпільовані states
       ↓
state modules
       ↓
зміна системи
```

Jinja працює до виконання states. Вона створює декларацію, але сама не керує ресурсами в тому сенсі, у якому це робить state module.

Важливе застереження: виклики `salt[...]` усередині Jinja виконуються на міньйоні просто під час рендерингу. Саме через них виявлення поточного стану найчастіше непомітно потрапляє в шаблон: результат execution module визначає структуру states ще до того, як state modules отримали шанс порівняти стан.

Тому цикл, який формує десять однотипних декларативних states, може бути цілком доречним. Але цикл, який реалізує алгоритм виявлення, перетворює конфігураційну модель або збирає послідовність команд, уже переносить програмну логіку в шар рендерингу.

## Проблема не в `if` і `for`

Сама наявність умов і циклів не є архітектурною помилкою. Наприклад, такий фрагмент лишається декларативним:

```jinja
{% for user_name, user_data in users.items() %}
user_{{ user_name }}:
  user.present:
    - name: {{ user_name }}
    - shell: {{ user_data.get('shell', '/bin/bash') }}
{% endfor %}
```

Цикл не обчислює спосіб керування користувачами й не перевіряє їхнє існування вручну. Він лише створює кілька декларацій `user.present` за вже підготовленими даними. Порівняння поточного й бажаного стану виконує state module.

Межу порушено, коли SLS починає:

- мігрувати або нормалізувати структури даних;
- реалізовувати правила злиття кількох конфігураційних моделей;
- самостійно виявляти поточний стан;
- будувати shell-команди як основну модель керування ресурсом;
- імітувати ідемпотентність через `grep`, `test`, `&&` і `||`;
- керувати тимчасовими станами й багатокроковим workflow;
- виконувати недетерміновані обчислення під час рендерингу.

## Правильний патерн: `map.jinja`

Перш ніж перейти до антипатернів, варто згадати приклад, який показує, як працювати з даними правильно. Класичний `map.jinja` із template-formula збирає підсумкову конфігурацію з фіксованих шарів:

```text
defaults.yaml
       ↓
значення, що залежать від ОС (osfamilymap, osmap)
       ↓
Pillar поверх усього
```

Це теж злиття даних у Jinja, але воно відповідає усталеній конвенції: порядок шарів відомий заздалегідь, правило одне — наступний шар накладається поверх попереднього, і будь-хто, хто знайомий із формулами Salt, розуміє результат без читання коду. Такий merge — частина контракту формули, а не прихований алгоритм.

Проблеми починаються там, де формула вигадує власні правила: мігрує схеми, розв'язує конфлікти, підтримує зворотну сумісність.

## Приклад 1. Нормалізація даних усередині SLS

Припустімо, формула підтримує нову й застарілу схеми конфігурації. У SLS з'являється такий код:

```jinja
{% if legacy_config is defined %}
  {% for category in supported_categories %}
    {% if category in legacy_config %}
      {% if category not in current_config %}
        {% do current_config.update({category: {}}) %}
      {% endif %}
      {% do current_config[category].update(
        legacy_config[category]
      ) %}
    {% endif %}
  {% endfor %}
{% endif %}
```

На відміну від `map.jinja`, цей блок:

- підтримує дві схеми даних;
- мігрує значення зі старої схеми в нову;
- створює відсутні вкладені структури;
- визначає власні правила злиття;
- змінює вхідні дані до компіляції states.

Це вже самостійна функція перетворення:

```text
legacy configuration
        ↓
normalization and merge
        ↓
current configuration
```

Таку функцію важко незалежно протестувати всередині SLS. Доводиться рендерити весь шаблон, готувати контекст Salt і аналізувати підсумковий lowstate, хоча предмет тестування — звичайне перетворення структури даних.

Логічніше винести нормалізацію в тестовану Python-функцію, наприклад в utility module:

```python
def normalize_config(current, legacy):
    """Return configuration converted to the current schema."""
```

Для неї можна окремо перевірити порожні структури, конфліктні значення, пріоритет нової схеми, невідомі параметри, повторний виклик і зворотну сумісність.

SLS при цьому отримує вже підготовлені дані й займається лише декларацією стану.

## Приклад 2. Саморобний state module на YAML, Jinja і shell

Інший поширений випадок — керування ресурсом через набір `cmd.run`:

```jinja
resource_create:
  cmd.run:
    - name: >
        tool list | grep -q "{{ resource_name }}"
        || tool create {{ resource_name }}

{% for key, value in resource_config.items() %}
resource_config_{{ loop.index }}:
  cmd.run:
    - name: >
        tool config set
        {{ resource_name }}
        {{ key }}={{ value }}
{% endfor %}
```

Тут SLS самостійно реалізує пошук ресурсу, перевірку його існування, створення, застосування параметрів, генерацію команд і частину логіки ідемпотентності.

Фактично це state module, реалізований засобами YAML, Jinja і shell. Salt не отримує повноцінної моделі ресурсу. Він бачить лише команди та їхній exit code.

Такий підхід створює кілька проблем. По-перше, `test=True` не може коректно показати план змін, якщо команда не реалізує власну безпечну перевірку. По-друге, зміна параметра часто виконується під час кожного запуску, навіть якщо потрібне значення вже встановлено. По-третє, помилки парсингу текстового виводу стають частиною моделі стану. По-четверте, shell quoting і спеціальні символи в даних створюють додатковий клас помилок.

### А як же `unless` і `onlyif`?

Природне заперечення: винести перевірку з shell в аргументи `unless`, `onlyif` або `creates`.

```yaml
resource_create:
  cmd.run:
    - name: tool create example
    - unless: tool show example
```

Це справді краще, ніж `grep ... ||` усередині команди: перевірка стає явною, а `test=True` принаймні не виконує саму команду. Але моделі ресурсу все одно немає. Під час пробного прогону Salt може повідомити лише «команду було б виконано», але не які параметри зміняться і з яких значень на які. `changes` лишається неструктурованим — stdout і exit code. Для окремих параметрів доводиться писати пари «команда + перевірка», і кожна така пара знову парсить текстовий вивід.

`unless` і `onlyif` — допустимий проміжний крок, але не заміна state module.

Бажана декларація має виглядати приблизно так:

```yaml
managed_resource:
  virtual_resource.present:
    - name: example
    - type: container
    - profiles:
        - default
    - config:
        limits.cpu: 4
        limits.memory: 8GiB
```

А state module має:

1. отримати поточний стан ресурсу;
2. нормалізувати його для порівняння;
3. порівняти з бажаним станом;
4. обчислити зміни;
5. повернути коректний результат за `test=True`;
6. застосувати лише необхідні операції;
7. повернути структурований `changes`.

SLS у такій моделі відповідає на питання «що має існувати», а state module — «як визначити й забезпечити цей стан».

## Приклад 3. Deployment workflow усередині infrastructure formula

Формула інфраструктурного сервісу може з часом почати виконувати таку послідовність:

```text
налаштувати репозиторій пакетів
        ↓
встановити пакет
        ↓
підготувати сертифікати
        ↓
завантажити розширення
        ↓
перезапустити сервіс
        ↓
дочекатися готовності
        ↓
виправити інтеграційний модуль
        ↓
перезавантажити модулі Salt
        ↓
увімкнути розширення сервісу
```

Окремі кроки можуть бути потрібні, але разом вони становлять не один постійний стан, а процедуру встановлення або оновлення.

Тут важливо розрізняти steady state і workflow. Steady state відповідає на питання: який пакет має бути встановлений, який конфігураційний файл має існувати, які permissions мають бути встановлені, які розширення мають бути ввімкнені, чи має сервіс бути запущений і доданий в автозавантаження.

Workflow відповідає на інші питання: у якій послідовності виконувати оновлення, коли тимчасово зупинити сервіс, коли ввімкнути compatibility feature, як дочекатися готовності, що робити в разі помилки, коли продовжити оновлення наступного вузла, як виконати rollback.

Постійний стан сервісу має лишатися в infrastructure formula. Спеціалізовані операції слід інкапсулювати в execution або state modules. Виправлення й розширення Salt потрібно постачати через Salt Extension. Послідовність оновлення, очікування й координацію між вузлами слід переносити в orchestration.

Якщо workflow лишити всередині звичайного SLS, повторний highstate може несподівано знову виконати частину процедури оновлення. Крім того, підсумковий файл стає важко читати: поруч опиняються декларація постійного стану, тимчасові дії та обхідні рішення для проблем конкретних версій.

## Приклад 4. Алгоритм, прихований в одному `cmd.run`

Іноді SLS виглядає коротким, але складність захована всередині однієї shell-команди:

```yaml
deploy_configuration_repository:
  cmd.run:
    - name: |
        [ -d /srv/config/.git ] || (
          initialize_repository &&
          configure_remote &&
          fetch_sources &&
          update_dependencies &&
          run_post_deploy_hook
        )
```

У реальному варіанті замість умовних функцій зазвичай стоять `git init`, створення посилань і hooks, налаштування remote, отримання гілки, ініціалізація submodules, оновлення залежностей і запуск post-deploy script.

Для Salt це одна дія. Система не бачить окремо стан репозиторію, потрібний remote, вибрану гілку, стан submodules, наявність hook і результат окремих кроків.

Перевірка `[ -d .../.git ]` також не означає, що репозиторій перебуває в потрібному стані. Каталог може існувати, але мати неправильний remote, застарілу гілку, пошкоджені submodules або відсутній hook.

Довжина SLS у цьому випадку оманлива. Один state приховує цілий алгоритм і кілька незалежних ресурсів. Більшу частину цього алгоритму вже покривають стандартні states:

```yaml
config_repository:
  git.latest:
    - name: https://git.example.com/config.git
    - target: /srv/config
    - rev: main
    - submodules: True

config_repository_hook:
  file.managed:
    - name: /srv/config/.git/hooks/post-merge
    - source: salt://config/files/post-merge
    - mode: '0755'
    - require:
      - git: config_repository

config_post_deploy:
  cmd.run:
    - name: /srv/config/bin/post-deploy
    - onchanges:
      - git: config_repository
```

`git.latest` керує remote, гілкою та submodules і коректно працює за `test=True`. `file.managed` відповідає за hook. Post-deploy script запускається через `onchanges` лише тоді, коли репозиторій справді змінився. Те, що не покривається стандартними states, слід інкапсулювати в спеціалізованому модулі з явною моделлю поточного й бажаного стану.

## Приклад 5. Недетермінований рендеринг

Ще один показовий випадок — обчислення випадкового значення під час рендерингу:

```jinja
certificate_reload_schedule:
  cron.present:
    - name: rebuild-certificate && restart-service
    - minute: {{ range(6, 54) | random }}
    - hour: 6
```

За однакових Pillar і grains два запуски можуть скомпілювати різні states. Перший highstate встановить одне значення хвилини, другий — інше, третій — знову змінить розклад.

Це порушує відтворюваність, передбачуваність highstate, стабільність dry run, можливість пояснити походження значення й відсутність змін під час повторного застосування.

Якщо завдання справді треба розподілити в часі, значення має бути детермінованим. Найпростіший варіант — стабільна функція від ідентифікатора вузла:

```jinja
    - minute: {{ salt['random.seed'](48, hash=grains['id']) + 6 }}
```

Кожен вузол отримує свою хвилину в діапазоні від 6 до 53, але для одного й того самого вузла вона не змінюється між запусками. Інші варіанти — явно передавати хвилину через Pillar або доручити розподіл зовнішньому scheduler.

Випадковість під час кожного рендерингу — це не бажаний стан.

## Приклад 6. Зовнішні дані через `cmd.run` і `curl` під час рендерингу

Іноді дані для формули отримують просто в шаблоні, викликаючи HTTP API через shell:

```jinja
{% set backends = salt['cmd.run'](
     'curl -s https://inventory.example.com/api/backends?role=web'
   ) | load_json %}

{% for backend in backends %}
upstream_{{ backend.name }}:
  file.managed:
    - name: /etc/nginx/upstreams/{{ backend.name }}.conf
    - source: salt://nginx/files/upstream.conf.j2
    - template: jinja
    - context:
        address: {{ backend.address }}
{% endfor %}
```

Виглядає компактно, але в такого коду одразу кілька проблем:

- запит виконується на міньйоні під час кожного рендерингу, зокрема за `test=True` і `state.show_sls`;
- результат рендерингу залежить від доступності й поточної відповіді зовнішнього сервісу, тож однакові Pillar і grains більше не дають однаковий state graph;
- `curl -s` без `--fail` повертає тіло помилки або порожній рядок, і формула або падає на розборі JSON, або мовчки генерує нуль states;
- немає таймауту, повторів і обробки помилок, а токен для API доводиться тримати в командному рядку, де він потрапляє в логи й список процесів;
- дані неможливо підмінити в тестах, не піднімаючи справжній сервіс.

Зовнішні дані мають надходити у формулу як вхідні дані, а не добуватися шаблоном. Найпряміший шлях — отримати їх на master через `ext_pillar`:

```yaml
# /etc/salt/master.d/ext_pillar.conf
ext_pillar:
  - http_json:
      url: https://inventory.example.com/api/backends?role=web
      namespace: inventory
```

Тоді SLS лише читає підготовлені дані:

```jinja
{% set backends = salt['pillar.get']('inventory:backends', []) %}

{% for backend in backends %}
upstream_{{ backend.name }}:
  file.managed:
    - name: /etc/nginx/upstreams/{{ backend.name }}.conf
    - source: salt://nginx/files/upstream.conf.j2
    - template: jinja
    - context:
        address: {{ backend.address }}
{% endfor %}
```

Якщо потрібна власна логіка запиту — авторизація, пагінація, фільтрація, нормалізація відповіді, — її варто винести у власний ext_pillar module або execution module з явним таймаутом, обробкою помилок і unit tests:

```python
def get_backends(role, timeout=10):
    """Return normalized list of backends for the given role.

    Raises CommandExecutionError if the inventory API is unavailable.
    """
```

В обох варіантах шаблон відповідає лише на питання, які upstream-файли мають існувати, а отримання й перевірка зовнішніх даних живуть у коді, який можна протестувати і який явно повідомляє про помилку.

## Контрприклад: умова, що лишається декларативною

Не кожне розгалуження слід виносити з SLS. Наприклад, вибір між фіксованою й останньою версією пакета, як і раніше, описує бажаний стан:

```jinja
service_package:
{% if package_version == 'latest' %}
  pkg.latest:
    - name: service-package
{% else %}
  pkg.installed:
    - name: service-package
    - version: {{ package_version }}
{% endif %}
```

Обидві гілки відповідають на одне й те саме питання: яка версія пакета має бути встановлена. Вони не реалізують ручне виявлення стану, не будують deployment workflow і не підміняють state module.

Так само допустимі прості цикли, що створюють однотипні декларації, і умови, що вмикають додатковий конфігураційний файл. Вимога тут не у відсутності логіки взагалі, а в збереженні декларативної моделі.

## Де має бути логіка

Щоб межа не залежала від особистого смаку автора формули, корисно розділяти відповідальність за типами компонентів.

### SLS

SLS відповідає за декларацію бажаного стану, композицію states, requisites між ресурсами, просте умовне ввімкнення states і генерацію однотипних декларацій за підготовленими даними.

SLS не повинен самостійно реалізовувати модель керованого ресурсу чи складний алгоритм підготовки даних.

### Pillar

Pillar містить вхідні дані: параметри оточення, версії, topology, списки ресурсів, feature flags, посилання на secrets і значення, специфічні для конкретного deployment.

Pillar — це дані, а не місце для виконуваних алгоритмів. Водночас pillar-файли теж рендеряться через Jinja, і в них легко розростається та сама логіка: міграція схем, злиття джерел, виклики `salt[...]`. Усі правила цієї статті стосуються й шаблонів pillar.

### Utility modules

Utility modules підходять для чистих функцій: нормалізації структур, міграції схем даних, злиття конфігурацій, перевірки й перетворення значень, обчислення похідних параметрів, формування спільної моделі, яку використовують кілька SLS.

Таку логіку можна тестувати звичайними unit tests без рендерингу всієї формули.

### Execution modules

Execution modules відповідають за операції та отримання даних від системи або зовнішнього API: запит поточної конфігурації, створення чи зміну ресурсу, виклик спеціалізованого CLI або API, виконання операції, якої немає в стандартних модулях Salt.

Вони надають повторно використовуваний Python API і приховують деталі transport, parsing та error handling.

### State modules

State modules пов'язують поточний і бажаний стан. Вони мають отримати поточний стан, визначити потрібний diff, підтримувати `test=True`, застосовувати лише необхідні зміни й повертати зрозумілі `result`, `changes` і `comment`.

Якщо SLS вручну виконує всі ці дії через `cmd.run`, це сильна ознака відсутнього state module.

### Salt Extensions

Salt Extension — це спосіб пакування, версіонування й доставки Python-компонентів Salt, наприклад execution, state, utility або runner modules.

Salt Extension не є окремим видом бізнес-логіки. Він дає змогу логіці, винесеній із SLS, мати власні залежності, тести й життєвий цикл.

Salt також підтримує простіший шлях: каталоги `_modules`, `_states` і `_utils` просто в репозиторії формули, які роздаються на міньйони через `saltutil.sync_all`. Це офіційно підтримуване рішення, але, на мою думку, не best practice: воно змішує Python-код із деклараціями й не дає чистої архітектури. Невеликий і легко тестований код може жити там і довго. Але щойно модуль росте, обростає залежностями або стає потрібним кільком формулам, його варто виносити в extension і тестувати окремо як звичайний Python-код.

### Orchestration

Orchestration відповідає за workflow між вузлами, ролями й зовнішніми системами: rolling update, виведення вузла з балансування, зупинку й запуск компонентів у заданій послідовності, очікування readiness, міграцію даних, перемикання трафіку, rollback і координацію кількох minions.

Orchestration описує процес. Звичайна formula описує стан окремої системи або компонента.

## Зв'язок з архітектурними шарами проєкту

Розподіл логіки за технічними компонентами доповнюється поділом Salt-проєкту на три рівні: Environment → Application Formula → Infrastructure Formula. Infrastructure Formula керує технологією — пакетами, конфігурацією, сервісами й універсальними ресурсами — і нічого не знає про клієнтів і бізнес-застосунки. Application Formula описує вимоги застосунку до інфраструктури через контракти infrastructure formulas. Environment описує конкретний deployment: які застосунки, на яких вузлах, у яких версіях і з якою topology.

Напрямок залежностей лишається однобічним, і жоден рівень не використовує SLS як заміну utility, execution або state modules. Детально цю модель буде розібрано в окремій статті.

## Практичний тест для SLS

Перш ніж додавати складний фрагмент у SLS, корисно поставити кілька запитань.

1. **Фрагмент описує результат чи процедуру?** Якщо він каже, який ресурс має існувати, це кандидат для SLS. Якщо він описує кроки, очікування, тимчасові стани й обробку переходів, це, імовірно, workflow.
2. **Дані вже підготовлені?** Якщо SLS лише проходить по готовій структурі й формує states, це нормальна композиція. Якщо він мігрує схеми, об'єднує джерела й розв'язує конфлікти, потрібна окрема функція нормалізації.
3. **Хто порівнює поточний і бажаний стан?** Якщо це робить state module, розділення збережено. Якщо SLS запускає CLI, парсить вивід і самостійно вирішує, чи виконувати наступну команду, він імітує state module.
4. **Чи працює `test=True`?** Користувач має побачити коректний план змін без їх застосування. Якщо це неможливо через непрозорий `cmd.run`, модель ресурсу перебуває не в тому шарі.
5. **Чи можна протестувати логіку незалежно?** Перетворення даних, validation або обчислення залежностей мають тестуватися без повного рендерингу highstate. Якщо для перевірки чистої функції доводиться запускати Salt renderer, її варто винести в Python.
6. **Чи дають однакові вхідні дані однаковий результат?** За однакових Pillar, grains і версій формул має компілюватися однаковий state graph. Випадковість, поточний час і нестабільний порядок зовнішніх даних порушують відтворюваність.
7. **Чи має код власний життєвий цикл?** Якщо компонент потребує окремих залежностей, версіонування, unit tests і повторного використання кількома формулами, його слід оформити як модуль і поширювати через Salt Extension.

### Як це перевірити на практиці

Запитання 6 перевіряється порівнянням скомпільованого результату двох прогонів:

```bash
salt-call --local state.show_lowstate --out=json > run1.json
salt-call --local state.show_lowstate --out=json > run2.json
diff run1.json run2.json
```

Порожній diff означає, що рендеринг детермінований. Запитання 5 закривається звичайним pytest: винесені функції з utility modules тестуються напряму, без Salt renderer і без піднятого міньйона.

## Підсумок

SLS лишається читабельною декларацією стану, коли вхідні дані мають зрозумілий контракт, перетворення й validation винесено в тестовані функції, операції інкапсульовано в execution modules, порівняння поточного й бажаного стану виконують state modules, багатокрокові процеси перебувають в orchestration, а однакові вхідні дані дають однаковий результат рендерингу.

Мета такого розділення — не заборонити Jinja чи зробити кожну формулу мінімальною за будь-яку ціну, а зберегти зрозумілі межі відповідальності. Кожен шар відповідає на своє питання:

- SLS — у якому стані має перебувати система;
- state module — як визначити розбіжність і привести ресурс до цього стану;
- utility і execution modules — як підготувати дані й виконати спеціалізовані операції;
- orchestration — у якій послідовності координувати зміни між системами.

Коли ці питання не змішано в одному шаблоні, формули простіше тестувати, безпечніше повторно застосовувати й легше розвивати в міру зростання інфраструктури.
