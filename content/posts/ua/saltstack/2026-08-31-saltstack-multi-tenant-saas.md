Уявіть: у вас є `billing` — монолітний PHP-застосунок, якому потрібні RabbitMQ, Redis, MySQL, PHP-FPM і веб-сервер. Продукт розгортається окремо для кожного клієнта. Приходить другий клієнт — і найпростіший шлях виглядає так: скопіювати папку зі states, поміняти пароль і домен, задеплоїти.

Через рік у вас п'ять форків одного й того самого коду. Виправлення в одному з них не потрапляють в інші. Ніхто вже не памʼятає, яка версія states насправді працює на проді в конкретного клієнта. А коли треба додати другий застосунок — `reporting`, який ще й залежить від `billing` — стає зрозуміло, що копіпаста більше не масштабується.

## З чого починаються проблеми

Перш ніж говорити про рішення, варто подивитись, куди зазвичай веде "просто зробити швидко".

**Копіювання формул у кожен клієнтський репозиторій.** Виправлення розходяться, ніхто не може сказати, яка версія коду реально задеплоєна, різні клієнти непомітно для себе отримують різну поведінку.

**Клієнтський `cmd.run` замість нормального стейту:**

```yaml
create-billing-user:
  cmd.run:
    - name: rabbitmqctl add_user billing password
```

Виглядає як швидкий фікс, але ламає ідемпотентність, ускладнює зміну пароля і розмазує логіку RabbitMQ по клієнтських проєктах — замість того, щоб вона жила в одному місці.

**Інфраструктурна формула, яка знає про застосунки:**

```yaml
rabbitmq:
  billing_defaults:
    ...
```

Щойно формула RabbitMQ дізнається про існування `billing`, вона перестає бути універсальною — і наступний застосунок, якому теж потрібен RabbitMQ, вже не зможе її просто переюзати.

**Формула застосунку, яка знає про конкретного клієнта:**

```jinja
{% if customer == "acme" %}
...
{% endif %}
```

Тут пастка підступніша: перший `if` виглядає нешкідливо, але клієнтські винятки мають звичку накопичуватись у спільному продукті, поки формула не перетвориться на нечитабельне дерево умов.

**Необмежена транзитивна залежність** — коли `billing-formula` тягне довільну версію `rabbitmq-formula` без фіксації. Salt сам по себе це безпечно не контролює, тож рано чи пізно прод одного клієнта отримає не ту версію, яку тестували.

Усі ці проблеми мають одну спільну причину: код керування технологією, код збірки застосунку і дані конкретного клієнта живуть впереміш в одному місці.

## Рішення: три рівні з чіткою межею відповідальності

Якщо розділити ці три речі по різних репозиторіях і зафіксувати напрямок залежностей — картина одразу спрощується.

```text
Клієнтський проект
       │
       ▼
Формула застосунку
       │
       ▼
Інфраструктурні формули
```

Залежності йдуть лише зверху вниз. `rabbitmq-formula` нічого не знає про `billing`. `billing-formula` нічого не знає про клієнта `acme`. Клієнтський проєкт не реалізує внутрішню логіку RabbitMQ — він лише каже, *які* ресурси потрібні і *де* вони живуть.

### Рівень 1 — інфраструктурні формули

`rabbitmq-formula`, `redis-formula`, `mysql-formula`, `php-formula`, `nginx-formula` — кожна керує одним технологічним продуктом і не має уявлення про застосунки, які нею користуються. Формула RabbitMQ вміє встановлювати пакет, керувати сервісом, плагінами, vhost'ами, користувачами, permissions і policies — але приймає лише універсальну структуру даних:

```yaml
rabbitmq:
  vhosts:
    /billing:
      present: true

  users:
    billing:
      password: secret
      tags: []

  permissions:
    billing@/billing:
      user: billing
      vhost: /billing
      configure: ".*"
      write: ".*"
      read: ".*"
```

Формула лишається формулою навіть якщо всередині є власні `_modules`, `_states` і `_utils` — окремий Salt extension має сенс, лише коли розширення використовується кількома незалежними формулами і має власний життєвий цикл. Для більшості SaaS-платформ достатньо звичайної SLS-формули з внутрішніми extension-модулями поруч.

### Рівень 2 — формула застосунку

`billing-formula` описує не технологію, а працездатний екземпляр продукту: PHP-FPM, конфігурацію, systemd-юніти для воркерів, міграції, health check — і те, які саме ресурси RabbitMQ/MySQL/Redis потрібні `billing`. Вона підключає інфраструктурні формули й перетворює прикладні дані (пароль користувача застосунку, назву черги) у структури, які розуміють формули першого рівня.

Тут є розвилка: або клієнтський Pillar одразу формує повний інтерфейс усіх формул (підхід A), або формула застосунку сама будує ресурси інфраструктурних формул зі свого, значно простішого Pillar (підхід B). Другий варіант зазвичай зручніший — клієнтський проєкт описує *що* потрібно `billing`, а не *як* влаштований RabbitMQ.

### Рівень 3 — Salt-проєкт клієнта

`customer-acme-salt` — це topology, targeting, вибір застосунків і профілів (shared чи dedicated), домени, feature flags, посилання на секрети і зафіксовані версії формул. Саме тут, і лише тут, зʼявляється клієнтська специфіка. Жодних `cmd.run`, жодного знання про внутрішній устрій RabbitMQ — тільки дані.

## Коли застосунків два, а RabbitMQ один

Найцікавіше починається, коли `billing` отримує сусіда — `reporting`, який залежить від `billing` і має свої власні вимоги до інфраструктури. Тут є два робочих варіанти топології.

**Спільний RabbitMQ-кластер** з окремими vhost'ами `/billing`, `/reporting` і, за потреби, `/integration` для міжпрограмної комунікації. Простіше в експлуатації, менше залізо, але застосунки одного клієнта певною мірою розділяють інфраструктурний ресурс.

**Окремі кластери RabbitMQ** для кожного застосунку — повна ізоляція, дорожче в підтримці, виправдано, коли вимоги до надійності чи навантаження суттєво різняться.

Вибір між ними — це вже не турбота ні `rabbitmq-formula`, ні `billing-formula`. Це рішення на рівні клієнтського проєкту: `shared` чи `dedicated` — просто ще один параметр у Pillar.

Повна картина для клієнта ACME з обома застосунками:

```text
Customer ACME
│
├── billing
│   ├── PHP-FPM
│   ├── MySQL database: billing
│   ├── Redis namespace: billing
│   └── RabbitMQ vhost: /billing
│
├── reporting
│   ├── PHP-FPM
│   ├── MySQL database: reporting
│   ├── Redis namespace: reporting
│   └── RabbitMQ vhost: /reporting
│
└── shared services
    ├── RabbitMQ cluster
    ├── MySQL cluster
    └── Redis cluster
```

І граф залежностей на рівні репозиторіїв дзеркалить архітектуру, з якої ми почали:

```text
customer-acme-salt
├── billing-formula
│   ├── php-formula
│   ├── mysql-formula
│   ├── redis-formula
│   └── rabbitmq-formula
│
├── reporting-formula
│   ├── php-formula
│   ├── mysql-formula
│   ├── redis-formula
│   └── rabbitmq-formula
│
└── customer-specific Pillar
```

## Секрети окремо від логіки

Ще одне правило, яке напрошується само собою: секрети не лежать відкритим текстом у Git. Джерелом може бути Salt Pillar з GPG renderer, Vault, SOPS чи будь-який external Pillar організації — формула застосунку в будь-якому разі отримує вже розвʼязане значення або стандартизовану посилання, а не токен доступу до Vault:

```yaml
billing:
  secrets:
    mysql_password:
      source: vault
      path: customers/acme/billing
      key: mysql_password
```

Конкретна реалізація renderer'а — деталь, яка не повинна протікати вище рівня клієнтського проєкту.

## Що з цього винести

Якщо звести все до практичних правил:

1. RabbitMQ, Redis, MySQL, PHP і Nginx — окремі інфраструктурні формули, які нічого не знають про застосунки.
2. Кожен SaaS-компонент — окрема формула застосунку зі своїм публічним Pillar-інтерфейсом.
3. Транзитивні залежності не підвантажуються автоматично — версії фіксуються на клієнтському або збірковому рівні.
4. Клієнтський Pillar відповідає лише за topology, налаштування і посилання на секрети — не за внутрішню логіку технологій.
5. Pillar interface і публічні state ID варто розглядати як версійований API, а не як внутрішню деталь.
6. Формули проходять CI до того, як їх версія потрапляє в клієнтську установку.
7. Клієнтські винятки лишаються в клієнтському проєкті — не просочуються в інфраструктурні чи прикладні формули.

Загалом схема виглядає так:

```text
                    VERSIONED BUILD / LOCK
                              │
                              ▼
┌──────────────────────────────────────────────────────────────┐
│ Client Salt Project                                          │
│ topology + targeting + customer Pillar + secrets references │
└─────────────────────────────┬────────────────────────────────┘
                              │ includes
                              ▼
┌──────────────────────────────────────────────────────────────┐
│ Application Formulas                                         │
│ billing-formula + reporting-formula                          │
│ product composition + application resources + integration   │
└─────────────────────────────┬────────────────────────────────┘
                              │ uses
                              ▼
┌──────────────────────────────────────────────────────────────┐
│ Infrastructure Formulas                                      │
│ RabbitMQ + Redis + MySQL + PHP + Nginx                       │
│ generic technology lifecycle and resources                  │
└──────────────────────────────────────────────────────────────┘
```

Три прості запитання, розведені по трьох рівнях — "як керувати RabbitMQ", "які ресурси RabbitMQ потрібні billing" і "де RabbitMQ клієнта ACME, shared він чи dedicated" — і копіпаста між клієнтськими репозиторіями просто перестає бути потрібною.
