Реліз 2026.2.3 [плагіна для SaltStack](https://plugins.jetbrains.com/plugin/30291-saltstack) об'єднує все, що накопичилося з 2026.2.1: перевірки для state-файлів, які вийшли в 2026.2.2, і нову велику частину для Pillar. Головна ідея релізу: IDE має ловити помилки, які зараз ви бачите тільки після `state.apply` або `pillar.items` на міньйоні. Нижче про головне.

## Pillar: валідація структури

Pillar-файл, який рендериться не в мапу, або `include:`, записаний не списком, Salt зламає під час рендеру. Тепер плагін бачить це одразу:

- корінь Pillar SLS має бути мапою. Хибні значення (`null`, `false`, `0`), які Salt сприймає як порожній Pillar, дозволені;
- `include:` має бути YAML-списком, а кожен елемент окремим записом;
- кілька YAML-документів в одному файлі тепер позначаються як помилка, а не попередження;
- корені, обгорнуті в Jinja-блоки (`{% if %}`, `{% macro %}`, блочний `{% set %}`), не дають хибних спрацювань.

Для типових помилок є quick fix: обгорнути скалярний `include:` у список або розбити елемент з кількома ключами на окремі. Відступи та коментарі при цьому зберігаються.

## Pillar: ключі по правилах YAML 1.1

Salt читає YAML за специфікацією 1.1, а потім працює з результатом як зі словником Python. Через це однакові для Salt ключі можуть виглядати зовсім по-різному. `PillarKeyValidator` нормалізує ключі так само, як це зробить Salt, і знаходить дублікати, які очима не помітиш:

```yaml
ports:
  80: http
  0x50: http-alt     # дублікат: 0x50 == 80
  1:20: legacy       # дублікат: шістдесяткове 1:20 == 80

flags:
  true: enabled
  1: one             # дублікат: у Python True == 1

names:
  a: plain
  "\x61": escaped    # дублікат: "\x61" декодується в "a"
```

Нормалізація розуміє десяткові, вісімкові, шістнадцяткові, двійкові та шістдесяткові числа, `.inf`, `.nan` і escape-послідовності в рядках у подвійних лапках. Крім дублікатів, валідатор перевіряє порожні ключі, зарезервовані імена та конфлікти типів. Щоб попередження не дублювалися, стандартна перевірка дублікатів YAML у Pillar-файлах вимикається, і працює тільки наша.

## Pillar: автодоповнення та навігація для `include:`

У `include:` тепер працює автодоповнення шляхів з `pillarRoots`, а Ctrl+Click веде на файл:

```yaml
include:
  - common.base   # → common/base.sls
  - apps          # → apps/init.sls
  -               # тут IDE запропонує доступні SLS
```

`init.sls` згортається до назви каталогу, як і в самому Salt. Якщо `pillarRoots` не налаштовано, плагін шукає каталог `pillar` у проєкті. State-файли й надалі використовують `fileRoots`, тож шляхи не перемішуються.

## `import_yaml` і `import_json`: дані, які IDE розуміє

Раніше після `{% import_yaml %}` змінна для IDE була просто чорною скринькою. Тепер плагін читає імпортований файл і:

- пропонує ключі, індекси масивів і вкладені поля;
- для ключів, які не можна записати через крапку (з дефісом, пробілом, крапкою або з цифри), вставляє дужкову нотацію: `defaults["log-level"]`;
- веде по Ctrl+Click на конкретний ключ або елемент списку в YAML/JSON-файлі;
- працює і тоді, коли імпорт лежить усередині `{% if %}`.

```jinja
{% import_yaml "defaults.yaml" as defaults %}
{{ defaults.nginx.workers }}        {# Ctrl+Click → ключ workers у defaults.yaml #}
{{ defaults.servers[0].host }}      {# елементи списків теж #}
```

Аналізуються тільки статичні звернення: якщо ключ обчислюється динамічно, плагін нічого не вигадує.

## Змінні SLS-контексту

Salt передає в кожен SLS набір змінних про сам файл. Плагін тепер знає їх усі: `sls`, `slspath`, `sls_path`, `slsdotpath`, `slscolonpath`, `tplpath`, `tplfile`, `tpldir` і `tpldot`.

Quick Documentation (Ctrl+Q) показує не тільки опис, а й значення, яке змінна матиме в цьому файлі. Наприклад, для `salt/web/nginx/init.sls`:

| Змінна         | Значення             |
|----------------|----------------------|
| `sls`          | `web.nginx`          |
| `slspath`      | `web/nginx`          |
| `sls_path`     | `web_nginx`          |
| `slsdotpath`   | `web.nginx`          |
| `slscolonpath` | `web:nginx`          |
| `tplfile`      | `web/nginx/init.sls` |
| `tpldir`       | `web/nginx`          |

Ці змінні існують тільки під час рендеру SLS. Тому у звичайних Jinja-шаблонах (наприклад, для `file.managed`) вони не пропонуються в автодоповненні, а їхнє використання підсвічується як невизначена змінна.

## State-файли: requisites, аргументи та цикли

Ця частина вийшла в 2026.2.2, і тут її варто згадати окремо.

**Requisites.** Додано підтримку `listen_in`, `onfail_all` і всіх `*_any` (`require_any`, `watch_any`, `onchanges_any`, `onfail_any`) з автодоповненням, валідацією та Quick Documentation. Wildcard-шаблони (`*`, `?`, `[ ]`) більше не дають хибних «unresolved ID». Голі state ID у requisites теж автодоповнюються й перевіряються. Скалярні значення там, де Salt чекає список (`require_in`, `require_any`), тепер помилка.

**Цикли в requisites.** `RequisiteCycleValidator` будує граф залежностей і знаходить цикли ще до запуску. Однакові ID у різних модулях (`pkg: nginx` і `service: nginx`) розрізняються правильно і хибних циклів не утворюють.

**Аргументи.** Типи аргументів state-функцій перевіряються за метаданими Salt: рядок, список, мапа, булеве значення, число. Глобальні аргументи розширено до 17 (`umask`, `parallel`, `reload_modules`, `reload_pillar`, `reload_grains`, `fire_event`, `saltenv` та інші), для всіх є автодоповнення, документація й перевірка.

**Структура декларацій і дублікати ID.** Плагін перевіряє, що в декларації одна функція на модуль і модулі не повторюються, і знаходить дублікати state ID у файлі та між файлами. ID, згенеровані Jinja, і `extend` у цій перевірці не враховуються.

## Продуктивність і стабільність

- Виправлено зависання UI на 17 секунд при відкритті налаштувань метаданих, якщо сервер метаданих відповідав повільно.
- Метадані Salt завантажуються у фоні, тож автодоповнення в state-файлах більше не блокує редактор.
- Додано звіти про помилки через Sentry та стандартний обробник помилок JetBrains Marketplace. Якщо щось впаде, ви зможете надіслати звіт прямо з IDE, і ми швидше це виправимо.
