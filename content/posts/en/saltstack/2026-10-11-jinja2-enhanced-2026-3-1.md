Anyone who has written Salt formulas in an IDE knows the moment: YAML is highlighted, Jinja is highlighted — and that's where the understanding ends. `grains['os_family']` is just a string. `salt['pillar.get']` is a mystery. `{% from "nginx/map.jinja" import nginx with context %}` — Ctrl+Click goes nowhere. And you only find out about a typo in a variable name when `state.apply` blows up on the minion.

The problem isn't that Jinja is hard. The problem is that Jinja in Salt isn't "just Jinja". It's Jinja with Salt's own context injected into it, its own functions, its own tags, and even its own syntax settings. A generic Jinja plugin can't know about any of that by definition.

That's the problem the **Jinja2 Enhanced 2026.3.1** release addresses.

## The core idea: the core doesn't know about the framework — and shouldn't

Previous versions understood Jinja as a language. Version 2026.3.1 adds around fifteen extension points through which a separate framework plugin can teach the core about its context: which variables exist in a given file, what types they have, which functions are available, where macros are imported from, which tags the environment adds.

For Salt, this means all of Salt's "magic" can live in its own layer on top of the Jinja core, instead of as a pile of hacks inside it.

## What this means in practice for Salt

Take a typical state:

```jinja
{% from "nginx/map.jinja" import nginx with context %}
{% import_yaml "nginx/defaults.yaml" as defaults %}

nginx-pkg:
  pkg.installed:
    - name: {{ nginx.package }}

{% if grains['os_family'] == 'Debian' %}
nginx-config:
  file.managed:
    - name: /etc/nginx/nginx.conf
    - source: salt://{{ tpldir }}/files/nginx.conf.j2
    - template: jinja
    - context:
        workers: {{ salt['pillar.get']('nginx:workers', 4) }}
{% endif %}
```

Almost every line of this snippet depends on what Salt knows, not what Jinja knows. Here's how the new extensions map onto it.

**Variables that aren't in the file.** `grains`, `pillar`, `opts`, `salt`, as well as `sls`, `slspath`, `tpldir` and `tplpath`, are declared nowhere — the renderer injects them. `ScopeVariableProvider` lets you declare such variables for a specific file, along with their type, precedence and shadowing rules. And context-aware inspection rules (`ContextAwareInspectionRuleProvider`) remove false "undefined variable" warnings in `.sls` files while keeping them in plain `.j2` files, where those variables really don't exist.

**Types and structure-aware completion.** `TypeSchemaProvider` describes expression types: collections, mappings, unions, callables. `dynamicTypeProvider` provides members that are known only from metadata. Together they make it possible to complete `grains['...']` with known keys and to flag access to a non-existent attribute. If a member exists only in metadata and has no file to navigate to, the plugin now creates a virtual declaration for it, so Ctrl+Click and documentation work for such members too.

**`salt['module.function']` as functions.** `functionProvider` registers callable globals with parameters, a return type and documentation. So `salt['pillar.get']` can come with a signature hint instead of remaining a black box.

**`map.jinja` and macros.** `symbolIndexContributor` and support for macro module providers make it possible to resolve `{% from "nginx/map.jinja" import ... %}` against Salt's file roots rather than the current directory. Navigation, completion and Find Usages work for symbols contributed by an extension plugin too.

**Salt's own tags.** `{% import_yaml %}`, `{% load_yaml as ... %}`, `{% import_json %}`, `{% load_text %}` are not standard Jinja. The assignment tag provider now gets semantic highlighting, so a variable declared via `load_yaml` looks and behaves like a variable.

**Custom delimiters.** Salt lets you override Jinja syntax via `jinja_sls_env` and `jinja_env`. `Jinja2ApiConfigProvider` sets the environment configuration per file: delimiters, extensions, syntax options. Inspections, highlighting and the parser now use the settings of the file that's actually open, rather than one global set for the whole project.

**References.** `referenceResolver` is the hook for context-aware reference resolution — for example, so that `salt://{{ tpldir }}/files/nginx.conf.j2` points to a real file.

**Range-precise injections.** Jinja in Salt lives inside YAML. The new position selectors in `InjectionLanguageProvider` let you specify exactly which part of the host PSI element a language is injected into. When several rules overlap, conflicts are resolved deterministically: by priority, provider and rule order.

**Quick fixes and live templates.** `quickFixProvider` lets a framework attach its own fixes, with preview and undo, to problems found by inspections — for example, replacing `pillar['key']` with `salt['pillar.get']('key', default)`. The live template context is now framework-aware too: a Salt state template shows up in `.sls` files, not in every Jinja file.

## Smaller, but useful

- Validation of `loop` attributes: `loop.index`, `loop.first` and `loop.revindex` are checked, and `loop.idnex` no longer slips through.
- Fixed a PSI read outside a read action in one of the UI listeners — the kind of bug that shows up rarely and always at the worst possible moment.
- Caching and invalidation of dynamic type metadata are more precise. When metadata changes, only what depends on it is refreshed.

## Why this matters for SaltStack specifically

Salt formulas are infrastructure code, and a mistake there costs more than a mistake in an HTML template. Today, most errors in `.sls` files are caught at render time on the minion: a typo in a pillar key, a non-existent attribute, a wrong path to `map.jinja`. Each one is a "commit → apply → read the traceback → fix" cycle.

Release 2026.3.1 doesn't turn the IDE into a Salt expert on its own. But it lays a foundation on which that can be built without compromises: the Jinja core is responsible for the language, and knowledge about Salt lives in a separate layer that plugs in through a public API. That's exactly the architecture I described in the [previous post](/en/saltstack/2026-08-31-saltstack-multi-tenant-saas) about the formulas themselves — clear boundaries of responsibility between layers. It turns out tooling needs the same thing.
