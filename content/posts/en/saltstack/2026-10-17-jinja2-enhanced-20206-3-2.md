Release 20206.3.2 of [Jinja2 Enhanced Support](https://plugins.jetbrains.com/plugin/29804-jinja2-enhanced-suppo) is almost entirely about extensibility. The plugin now understands templates better out of the box, and frameworks and libraries can more easily teach it their own rules: how templates are found, which filters are available, and what types variables have. Here are the highlights.

## Template Resolver API: templates where your framework expects them

Every framework has its own rules for finding templates: app prefixes, namespaces, multiple directories, virtual paths. Until now, the plugin could only guess. The new **Template Resolver API** (`Jinja2TemplateResolver`) lets an extension:

- turn the string in `{% include %}`, `{% extends %}`, or `{% import %}` into an actual file;
- offer its own path completion;
- claim a path: once a resolver takes ownership of a path, nothing else interferes; if it doesn't, the default lookup logic applies.

The API comes with a new **unresolved template inspection**. It highlights paths that no resolver could resolve and separately flags dynamic expressions that can't be checked statically. It stays quiet when a missing file is referenced on purpose:

- `{% include "optional.html" ignore missing %}` is left alone;
- in a fallback list such as `{% include ["custom.html", "default.html"] %}`, a missing first entry is not reported if a fallback resolves.

## Multi-target navigation

Sometimes a single path points to several files: overridden templates, multiple directories, different themes. In that case, Go to Declaration now shows a list where each target has its own description and icon, so you can see exactly where you're going.

## Precise reference handling: `user.address["city"]`

We rewrote access-chain analysis. An expression is now split into segments, and each one keeps its original syntax: dot access, index, or string key. Every PSI reference knows exactly which segment it points to. Quoted keys are decoded, so `data["my-key"]` and `data['my-key']` are treated the same.

For users, this means more accurate completion, navigation, and type hints in long expressions. Extension authors get `Jinja2AccessSegment`, `referenceSegmentIndex`, and a new context for assignment tags (`Jinja2AssignmentTagContext`).

## Type inference that doesn't get lost along the way

Previously, a variable's type was often lost after the very first transformation. Now it propagates through:

- assignments (`{% set %}`);
- subscripts;
- filters;
- function and macro calls;
- conditional expressions.

```jinja
{% set first = users | first %}
{% set name = first.name if first else "Guest" %}
{{ name | upper }}   {# the plugin knows this is a string #}
```

## Deprecated filters and tests

A filter or test can now be marked as deprecated, with metadata on what replaces it and which version deprecated it. The plugin strikes it through in the editor, reports it with an inspection, and takes it into account in navigation and type inference. This helps libraries that are evolving their API gradually.

## Metadata Source API and `.jinja2-metadata.json`

The biggest addition in this release is the declarative **Metadata Source API**. You can now describe variables, filters, tests, functions, and their types in a metadata file, with no plugin code required.

Built-in support for `.jinja2-metadata.json` includes:

- a JSON Schema, so completion and validation work right in the IDE;
- VFS tracking, so changes take effect immediately with no restart or manual reindexing;
- a *New → File* template for creating one.

This is a good fit for teams that want to describe their template context (for example, the variables passed in by the backend) and get full code insight.

## File-scoped symbols: `appliesTo`

Filter, test, and function providers can now use `appliesTo` to declare which files they apply to. Framework-specific filters show up only in that framework's templates and no longer clutter completion in other projects. There is also a new utility that finds the host file for templates embedded in other languages.

## Under the hood

- **`Jinja2ProviderLifecycle`**: a single mechanism for cache invalidation and reindexing across all providers. Every provider now has a `ModificationTracker`, so data refreshes on time without unnecessary recomputation.
- **Original source coordinates in the completion context.** Providers now know the exact caret position in the source file, even when the template is embedded in another language.
- The release workflow has been updated with container builds and improved Sentry integration. The ProGuard configuration was also fixed for the new inspection.

## For extension authors

All new APIs are documented, with dedicated resolver guides, examples, and tests. Existing type providers keep working as before because `resolveType` stays backward-compatible.

Update via *Settings → Plugins* or on the [plugin's JetBrains Marketplace page](https://plugins.jetbrains.com/plugin/29804-jinja2-enhanced-suppo), and let us know what we should improve next.
